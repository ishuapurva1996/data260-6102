# AI use — Part 3

1. **What AI assisted with, and what the user supplied.** The user supplied the existing repository, correct HW3 baseline, assignment, implementation plan and shared contract. Codex implemented the Part 3 generator, ownership guard, two query strategies, request-local SQL instrumentation, benchmark/summarizer, index experiment, tests and evidence fragment. Bounded agents helped with separate modules and review. The shared backend came from the Part 2 session. This fragment does not claim the user manually wrote or independently tested these additions.
2. **One output independently checked.** We checked whether the deliberately naive endpoint really executes one manager SELECT per rental when many rentals share the same manager. An ORM identity map can return an already loaded object, so a plausible-looking N+1 implementation can undercount the intended queries. We also checked that auth and session activity are included in total SQL.
3. **How it was checked.** Tests used the real MySQL instance and the foundation's real auth dependency. A separate SQLAlchemy execution listener compared every executed statement with the response headers. Another test temporarily assigned repeated manager IDs and one null manager under a transaction, then rolled it back. Concurrent requests checked that counters did not leak between requests. Full payload equality, generated-versus-stored dataset hashes, and independently recomputed raw-data summaries provide additional checks.
4. **What changed and why it works.** The naive route uses explicit SELECT statements instead of `Session.get` or lazy relationship access. The fixed route materializes the same fields through one left join. A mutable request-local counter covers thread-pool dependencies and serialization. Review removed repeated dataset/baseline hashing while keeping the evidence checks. No timings, SQL counts or Postman images were invented; the six Postman screenshots remain explicitly pending manual access.

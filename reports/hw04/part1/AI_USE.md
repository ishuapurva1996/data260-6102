# Part 1: AI use and verification

1. **What the assistant did and what I did.** The user supplied the assignment, implementation plan, shared API contract, correct HW3 baseline, and ownership boundaries. Codex implemented the React client and browser checks, coordinated the backend foundation merge, ran the tests, captured screenshots, and drafted this report section. A separate Codex worker wrote the browser runner; review workers inspected the frontend. This record does not claim that the student independently wrote or manually tested the generated code. The student still needs to review the submission and its explanation.

2. **An unsuitable AI output and an independently checked result.** The first generated form wrapped the property-type select and description textarea inside their labels. In the browser checks, those labels did not remain stable for exact accessible-name lookup after their contents changed. The first generated real-browser test also tried to read the body of a 204 response after the page navigated. Chromium reported that the body was unavailable. These were actual failures, not hypothetical examples. Separately, the runtime checks confirmed that a saved listing and login survived a real server restart.

3. **How the problems were detected.** Playwright exercised the rendered controls by their labels, submitted the forms, inspected outgoing HTTP requests, and checked the resulting page. The first mock runs failed at the select and textarea lookups. The real run failed at `response.text()` after deletion. Raw failed-attempt logs are retained beside the successful results. The persistence check kept the browser open, stopped the owned server process, started a new process, refreshed the browser, and checked the stored listing again.

4. **What changed and why it now works.** The select and textarea now use explicit `htmlFor`/`id` pairs, which associate a stable label with each control. The DELETE check now checks status 204 and the absence of a nonzero Content-Length, then verifies that a GET of the deleted ID returns 404. The runtime runner also checks deletion after another server restart. A broad test-only URL interception rule was narrowed to paths beginning `/api/` so it does not intercept the development source module `/src/api/client.js`. The managed runtime uses reusable local sockets for restart and bounded process-group cleanup. The selected results record successful mock, real MySQL, and expiry checks separately.

The assistant used the provided teaching demo for the React component/props pattern, not its user-ID login. The final runtime has no mock backend or local session token. No password, live cookie value, or database connection string is intentionally stored in the report, screenshots, or coordination handoff.

Review also identified late-response races and a process-cleanup gap. Codex added regression checks, observed an actual pending-Cancel failure before fixing it, and reran all selected tests on committed code. The final mock suite has 19 checks. A real SIGTERM experiment verified that the runtime runner stops its owned server and records an interrupted run.

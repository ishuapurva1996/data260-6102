2. **What output was unsuitable, or what was independently checked?** One AI review suggested removing the dictionary-type checks around decoded session data because Starlette supposedly guarantees a dictionary. That suggestion was wrong for the pinned middleware: after verifying a signature, it decodes JSON without checking its shape. A separate check also found that the first browser evidence script assumed a nonexistent package-lock.json.
3. **How was it checked?** The middleware source and tests with signed arrays, null, strings, and numbers were inspected. Real TestClient requests demonstrated that these payloads are rejected without granting dashboard access. The browser script's actual ENOENT error identified the incorrect lockfile assumption. This was automated verification performed by the AI-assisted session, not a claim of an independent student audit.
4. **What changed, and why does it work now?** The defensive type checks were retained; invalid shapes are cleared and redirected to login. The evidence manifest now lists files that actually exist. In addition, the tutor's cookie-clearing logout was extended with server-side revocation. Tests copy a valid cookie, log out or reach the idle boundary, and deliberately replay the copied cookie from a fresh client. The dashboard checks the registry and denies it even when the signed token is otherwise valid. Actual HTTPS browser replay checks complement the deterministic unit tests.

Part 1 uses no language or embedding model at application runtime and no paid API. AI assistance concerns implementation and writing only. Part 2 and final report assembly belong to separate sessions.
